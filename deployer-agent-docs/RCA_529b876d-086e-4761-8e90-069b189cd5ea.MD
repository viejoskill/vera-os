# RCA — "Liquidaciones" menu missing for inmovarelacde@gmail.com (production)

## Problem statement
One non-admin user (inmovarelacde@gmail.com) cannot see the "Liquidaciones" menu section in production, while the admin's unrelated 'Editar datos' fix deployed fine. Need to determine if it's a CDN/edge cache issue serving a stale JS bundle vs. something else.

## Verdict
It is **NOT a CDN/edge caching problem and NOT a backend error**. It is a **production database data mismatch**: this user's `app_access` document in production has **no `sections` field**, so the menu correctly falls back to default sections that exclude Liquidaciones.

## Evidence

### 1. Deploy is complete & live bundle is current (not stale)
- Active run `529b876d` (redeploy) = SUCCESS, promoted, serving `https://real-estate-os-10.emergent.host`. Frontend type = cloudflare (static from R2).
- `GET /` serves real app HTML (Varela Inmobiliaria), referencing hashed bundle `/static/js/main.aee518b9.js`.
- Live bundle contains the current permission logic: grep of the served JS → `liquidaciones`(5), `Liquidaciones`(3), `sections`(22), `isAdmin`(7), `approval`(12). The current build IS live.

### 2. Cache headers are correct — a plain reload gets the fresh app
- `index.html`: `Cache-Control: no-cache, no-store, must-revalidate` → never cached at edge or browser; every reload refetches it.
- Hashed JS `main.aee518b9.js`: `Cache-Control: public, max-age=31536000, immutable` → correct/safe, because the filename hash changes per build (standard cache-busting). Since index.html is always re-fetched, a new deploy's new hash is always picked up.
- **No service worker / PWA app-shell cache** in the source (grep for serviceWorker/workbox/sw.js = none), so nothing can pin an old bundle across a reload.
=> No mechanism exists for a regular browser reload to serve a stale bundle to any client.

### 3. Backend endpoint is healthy
- Production logs: `POST /api/auth/approval` → `200 OK` (x3), no 5xx. (An httpx traceback in logs is from a MercadoLibre OAuth token call — unrelated.)

### 4. ROOT CAUSE — production data is missing `sections`
- Frontend calls **POST** `/api/auth/approval` (AuthProvider.tsx L74), re-run on every mount/reload keyed on session email — so approval is re-fetched on a plain reload (logout/login not required for refresh).
- Live POST for her email returns: `{"email":"inmovarelacde@gmail.com","approved":true,"isAdmin":false,"sections":null}` — **sections is null**.
- Production DB (`mongo_query`, db `real-estate-os-10-base`, collection `app_access`) document: `{"_id":"inmovarelacde@gmail.com","approved":true,"email":"inmovarelacde@gmail.com","isAdmin":false}` — **no `sections` field at all**.
- Gating logic (AppLayout.tsx L24/L35-37):
  - `employeeSectionIds = approval?.sections ?? ['alquileres','studio']`
  - sidebar items = navRoutes filtered by `r.enabled !== false` then `employeeSectionIds.includes(r.id)`.
  - With `sections: null`, the `??` falls back to the DEFAULT `['alquileres','studio']`, which does NOT include `liquidaciones` → menu item hidden. Working exactly as designed given the data.

### 5. Why the owner thought the data was correct
- Production's endpoint only accepts POST; `GET /api/auth/approval?email=...` returns **405 Method Not Allowed** in prod. The owner's "GET returns the right payload" + the `sections:["liquidaciones"]` document were observed in **PREVIEW**, whose database is separate from production. The sections assignment was never applied to the PRODUCTION data for this user.

## Fix
- **User (admin), production data:** Assign the Liquidaciones section to this user **in production** — log into the live production app (https://real-estate-os-10.emergent.host) as the admin and use the "Equipo" screen to set her sections to include `liquidaciones` (writes `sections` on the prod `app_access` doc). Alternatively, set `sections: ["liquidaciones"]` on the production `app_access` document `_id = inmovarelacde@gmail.com` directly. After that, a normal page reload will pick it up (approval is re-fetched on load).
- No code change and no redeploy needed; frontend + backend behave correctly once the prod data has `sections`.

## Explicitly ruled out
- CDN/edge cache serving stale bundle: ruled out (index.html no-store; immutable hashed assets with per-build hash; no service worker).
- Stale/old deploy: ruled out (active run live, current logic present in served JS).
- Backend 5xx on approval: ruled out (200 OK in logs).
