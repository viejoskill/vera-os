# RCA — Deploy run 00f0925a-96fd-49e8-bdad-73a7db51910a (redeploy, real-estate-os-10)

## Summary
The deploy failed at **build_image** during the frontend compile (`yarn build`). It is a **TypeScript type error (TS2322)** in the app source, caused by a **duplicated `@types/react`** in the dependency tree. This is a code/dependency fix owned by E1 — it is NOT a manifest or platform issue, and no secret/tier/infra change is involved.

## Failing step
- Step: `build_image` (Cloud Build `268f9f6d-7111-4780-b9c6-51a9d7e997f3`), step #2 `docker-build`, stage `frontend-build 12/13` (`yarn install && yarn build`).
- Compiler output:
  ```
  Failed to compile.
  TS2322: Type 'false | ReactPortal' is not assignable to type 'ReactNode'.
    Type 'ReactPortal' is not assignable to type 'ReactNode'.
      Type 'import(".../@types/react-dom/node_modules/@types/react/index").ReactPortal'
        is not assignable to type 'React.ReactPortal'.
  ```
- Location: `frontend/src/app/screens/TasacionesScreen.tsx`, line ~490:
  ```tsx
  {showMapaZona && createPortal(
     <div className="vera-modal" ...> ... <Check size={15}/> Listo ... </div>,
     document.body,
  )}
  ```

## Root cause (proven)
From `frontend/package.json` and `frontend/yarn.lock` (read in sandbox):
- `package.json` pins: `react` / `react-dom` / `@types/react` / `@types/react-dom` all at `19.0.0`.
- `yarn.lock` contains TWO `@types/react` entries:
  - `@types/react@19.0.0` → version **19.0.0** (direct dev-dependency, hoisted to root).
  - `@types/react@*` → version **19.2.17** — pulled in because `@types/react-dom@19.0.0` declares `dependencies: { "@types/react": "*" }`. The floating `*` resolved to the newest published build and got nested under `@types/react-dom`.
- `createPortal` is typed via react-dom's nested `@types/react@19.2.17`, whose `ReactPortal`/`ReactNode` is a structurally different type than the root `@types/react@19.0.0`. TypeScript therefore rejects the portal expression as not assignable to `ReactNode` → TS2322.

### Why it worked on 11-03 but fails now
Same source compiled on the prior successful run (ef0f4990, 2026-11-03). The build reinstalls deps with `--check-files`, so the unpinned `@types/react@*` (from `@types/react-dom`) re-resolved to a NEWER version (19.2.17) than before, introducing the second, incompatible copy. This is dependency drift on a floating transitive range — not a source change by the user.

## Recommended fix (E1 — code / package.json)
Force a single `@types/react` across the whole tree by pinning it in `frontend/package.json` `resolutions` (the block already exists):
```jsonc
"resolutions": {
  ...existing entries...,
  "@types/react": "19.0.0",
  "@types/react-dom": "19.0.0"
}
```
Then regenerate the lockfile (`yarn install`) so the nested `@types/react@*` collapses to `19.0.0`. This removes the duplicate `ReactPortal`/`ReactNode` definitions and resolves TS2322. Re-deploy after.

### Note on an insufficient workaround
Converting `{showMapaZona && createPortal(...)}` to a ternary `{showMapaZona ? createPortal(...) : null}` only removes the `false` arm of `false | ReactPortal`; it does NOT fix the underlying duplicate-types incompatibility (the nested `ReactPortal` is still not assignable to the root `ReactNode`). The dedupe via `resolutions` is the real fix.
