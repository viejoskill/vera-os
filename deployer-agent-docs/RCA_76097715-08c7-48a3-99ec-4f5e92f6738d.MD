# RCA — VERA OS high CPU / slow response time in production

**Deployment:** real-estate-os-10 (`varelapropiedadescde.com.ar` / `real-estate-os-10.emergent.host`)
**Active run:** 76097715-08c7-48a3-99ec-4f5e92f6738d
**Symptom (from Monitorización dashboard):** CPU utilization >85% across many intervals over 24h; response time "Crítico" — 3.9s avg, 6s peak.
**Verdict:** This is BOTH a code inefficiency and an undersized/non-autoscaled tier. The code path massively amplifies per-request CPU; the tier has no headroom to absorb it. It is NOT a crash, NOT OOM, and NOT a regression from the recent Alquileres/Liquidaciones work.

---

## What was ruled OUT (with evidence)
- **Memory pressure / GC / OOM:** `get_pod_events` → pod `Running`, `restart_count: 0`, no `OOMKilled`, no kill findings. Memory limit 512Mi is not being hit. Not a memory issue.
- **Crash loop:** no restarts, no CrashLoopBackOff.
- **Digest-email scheduler / runaway loop:** `rentals_bot._scheduler_loop()` sleeps 300s and only does work at 09:30 and 16:30 AR time (idempotent, guarded by a DB marker). Negligible CPU. Not the driver.
- **Recent code regression:** the hot path is the public listings endpoint, independent of the Alquileres/Liquidaciones screens. Consistent with the user's note that nothing in recent work touched public pages/heavy loops. This is a pre-existing inefficiency exposed by traffic.

---

## Confirmed root cause #1 — Inefficient public endpoint (CODE, highest leverage)

`GET /api/public/listings` in `backend/routes_public.py` is the hot path (public site + Google Ads/GTM traffic + `crawler_enabled=true`). Per request it does:

1. **Full, unbounded portfolio fetch on every request — no response cache.**
   `property_repository.list_properties(status="all")` runs a PostgREST query `select=*, property_images(*)` over ALL non-archived properties with ALL their image rows — no `limit`, no pagination (confirmed in `property_repository.py`).
   - Evidence in logs: `GET .../rest/v1/properties?select=*,property_images(*)&order=created_at.desc&archived=eq.False` repeating every ~2s (01:00:57, :59, 01:00, :02, :05).

2. **Serial signed-URL generation, one blocking round-trip per property.**
   The endpoint loops over every row and calls `await property_to_response(r)`, which signs the cover image via `_sign(...)`. The loop is sequential (`for r in rows: await ...`), so N properties = N serial network calls to Supabase storage.
   - Evidence in logs: a burst of ~30 sequential `POST .../storage/v1/object/sign/property-images/...` calls spread over ~7s (01:00:42 → 01:00:49), each ~200ms apart.

3. **The in-memory cache only partially helps.**
   `serializers._SIGN_CACHE` caches signed URLs only (TTL ≈ SIGNED_URL_TTL_SECONDS − 300 ≈ 55 min), and it is **per-process** — not shared across the 2 replicas, and it does NOT cache the Supabase fetch or the per-property pydantic serialization. So the expensive work (full fetch + `model_dump(by_alias=True)` for every property + sign storm on cold cache / cache rollover / new replica) recurs.

Net effect: each public page hit = 1 full-table fetch + up to N serial network round-trips + N pydantic serializations, executed on a **0.25 vCPU** cap. Under real visitor + bot traffic (each page also fires `POST /api/analytics/track`), this saturates CPU and produces the multi-second response times the dashboard flags.

### Suggested code fixes (E1)
- **Add a short-TTL in-process response cache for `/api/public/listings`** (e.g. 30–60s). Repeated public/bot hits should serve a cached payload instead of re-fetching + re-serializing + re-signing the whole portfolio every time. This alone should collapse the CPU load.
- **Sign cover images in parallel** with `asyncio.gather` instead of the serial `for`-loop (the detail endpoint already does this via `property_to_detail`).
- Optionally **paginate/limit** `list_properties` for the public view and/or precompute a lightweight listings payload on property change rather than on every read.
- Consider lightly rate-limiting or debouncing `/api/analytics/track`, which fires on every public page view.

## Confirmed root cause #2 — Undersized, non-autoscaled tier (USER / resources)

`get_tier`: tier_0 "Starter" — CPU request **50m**, CPU **limit 250m (0.25 vCPU)**, memory 200Mi/512Mi, **replicas 2, max_replicas 2, hpa_enabled=false (no autoscaling)**.

For a public-facing real estate site with external/ad/crawler traffic, 0.25 vCPU per pod with a fixed 2 replicas and no autoscaling has no headroom to absorb traffic spikes — directly consistent with the dashboard's sustained >85% CPU and critical response times. Even after the code fix, a public site will benefit from more CPU and room to scale.

### Suggested action (User)
- Raise the tier in **Deployment Panel → Resources** (tier_1 "Launch" or higher) to increase CPU per pod and headroom. Note autoscaling (HPA) is currently off at tier_0.

---

## Priority
1. Apply the **code fix** (response cache + parallel signing on `/api/public/listings`) — this is the primary driver and the highest-leverage change.
2. **Upgrade the tier** for sustained public traffic headroom.

Verification note: diagnosis is from production logs, pod events and tier config; the per-request amplification was confirmed by reading the source in a sandbox. I did not load-test the fix.
